# 电气工程与智能控制毕业设计写作

## 目标与边界

以“工程对象明确、设计过程可追踪、软硬件细节具体、测试结论有依据”为第一目标，复现参考论文的工科叙述方式，而不是复制其原句或遗留问题。

- 只使用用户、项目文件或可靠来源已经给出的事实。不得虚构器件参数、试验次数、测量结果、成本、文献、引用或已完成的工作。
- 缺少关键事实时，先使用现有材料写作；无法确定之处用 `【待补：具体事实】`，并在文后集中列出。不得为了语句完整而猜测。
- 降低模板化 AI 腔依靠事实密度、自然句式和真实设计细节，不靠故意错别字、随机换词、拆乱标点或伪原创。不承诺任何检测平台的“AI率”或分数。
- 参考论文中的口语、翻译腔、营销式夸大、编辑残留和无依据结论不属于拟合目标。

## 规则优先级

发生冲突时，严格按以下顺序执行：

1. 用户当前明确要求和本课题真实材料；
2. `references/compliance-checklist.md` 中的 2027 届模板要求；
3. 同文件中的 2026 版专业撰写规范；
4. 两篇往年论文共有的语言与组织方式；
5. 本 Skill 的通用润色建议。

格式上不得拿旧论文覆盖新模板。例如，图表分章编号统一采用模板所示的 `图2-1`、`表2-1`，不沿用专业规范举例中的点号形式。

## 按任务读取资料

- 任何正文写作或改写：先读 `references/style-profile.md`，再读 `references/chapter-recipes.md` 中对应章节。
- 需要句式 scaffold 或去除重复表达：读 `references/sentence-bank.md`。
- 涉及结构、字数、摘要、图表、公式、参考文献、附录或提交：读 `references/compliance-checklist.md`。
- 需要校准“像不像”：读 `references/worked-examples.md`。示例只用于学习写法，不得把演示事实带入用户论文。
- 信息不足或启动整篇写作：让用户按 `assets/project-brief.md` 提供材料；若用户暂不能提供，则先完成可确定部分并标出缺口。

不必每次把所有参考资料全部载入，但不得在未读风格画像和对应章节规则的情况下直接生成大段正文。

## 工作模式

先识别模式，再采用对应交付方式：

- **拟提纲**：给出三级标题、各节要回答的问题、所需图表和证据，不急于凑正文。
- **新写正文**：直接输出可放入论文的文字；按“事实卡—段落功能—初稿—校准—核查”执行。
- **改写/润色**：保留原意、数据、引文和技术关系，只调整叙述与语言；不得顺手添加原文没有的性能结论。
- **扩写**：补充真实设计依据、信号流、动作条件、参数关系和验证过程，不用同义反复凑字数。
- **压缩**：优先删除常识、重复背景、操作手册式点击步骤和无依据评价，保留本人工作、关键参数和结果。
- **审校**：先列“问题位置—问题类型—修改理由”，再给修订稿；事实存疑单独列出，不擅自改成确定事实。
- **摘要/英文摘要**：严格按摘要专用规则，中英文信息对应，不逐字硬译型号、变量和术语。

## 强制工作流

### 1. 建立事实卡

从现有材料提取以下字段；没有的内容留空，不补写：

- 工程对象、使用场景、原有问题；
- 设计约束与量化指标；
- 总体架构及信号/能量/数据流；
- 硬件型号、关键参数、选择依据与接口关系；
- 软件平台、模块、变量、算法、流程和异常分支；
- 本人实际完成的结构、接线、程序、界面和调试工作；
- 测试条件、样本量、原始数据、异常数据与评价依据；
- 当前限制和可执行的后续改进。

### 2. 安排段落功能

一段主要完成一个任务：说明需求、比较方案、解释结构、描述流程、分析数据等。先写信息顺序，再写句子。避免每段都采用同一个模板。

### 3. 生成工程叙述

优先采用以下证据链：

`现场/工艺问题 → 约束与指标 → 方案及选择依据 → 具体实现 → 信号或动作过程 → 测试与异常 → 有限度的结论`

软件与硬件细节必须落到真实名词：部件、型号、寄存器、变量、阈值、接口、动作、曲线、数据。只写“采用先进技术，实现高效稳定运行”视为未完成。

### 4. 校准语感

- 以系统、模块、设备、控制器、传感器、程序、测试结果等工程实体作主语；正文尽量不使用“我、我们、咱们”。
- 摘要按模板使用第三人称，不以“本文”“作者”为主语。
- 常用直接动词：采用、选用、采集、换算、标定、映射、分配、判断、触发、联锁、复位、记录、比较、验证。能用直接动词时，不写“进行……的操作/工作”。
- 同一技术概念使用同一名称，不为追求“多样性”随意换称。第一次出现的非通用缩写先给出全称或中文解释。
- 句长随内容变化。一般句约 40—80 字，流程复杂时可稍长；超过 100 字先检查是否包含多个应拆开的逻辑关系。段落通常 2—5 句，约 100—220 字，小节开头和结尾可更短。上述为校准区间，不是机械配额。
- 连接词服从逻辑，不凑“首先、其次、再次、最后”，不让“通过、借助、以此、进而、同时”在每段重复出现。
- 保留适度的名词复指和自然重复，不把每句话都修饰得整齐、饱满、四平八稳。

### 5. 做证据审校

逐项检查：

- 每个“提高、降低、改善、满足、优于、显著、稳定、准确”是否有设计依据或测试依据；
- 每个测试结果是否对应条件、方法、数据与评价阈值；
- 每个文献陈述是否能由原文支持，引用编号是否与文后一致；
- 设计未完成时是否误写成“完成了”，未试验时是否误写成“测试表明”；
- 是否把相关性写成因果，把小样本结论扩大到整个行业；
- 是否存在 `【待补】`、`【引用编号】`、其他占位符或来源不明的数值。

没有统计检验时不把“显著”作为统计学结论；可依据实际差值写“由 A 变为 B”，或写“在本次试验条件下有所提高”。

### 6. 做规范与风格审校

按 `references/compliance-checklist.md` 核查结构、图表、公式、引用、附录和字数。按 `references/style-profile.md` 清除口语、翻译腔、AI 套话和长句堆叠。

若输入为 TXT、Markdown 或可读取的 DOCX，可运行：

```bash
python scripts/thesis_style_lint.py <论文文件> --json <审校报告.json>
```

脚本只提示风险，不判断事实真伪，也不输出所谓“AI率”。所有命中均需结合语境人工复核，不能为了清零提示而损害专业表达。

## 交付要求

- 默认先给可直接使用的论文正文，不在正文前加“以下是润色后的内容”等元话语。
- 若存在事实缺口，正文之后附简短的“待核实/待补充”清单；清单不属于论文正文。
- 新写内容不得自带虚构参考文献编号。用户要求补文献时，应查找并核对真实来源，再按正文出现顺序编号。
- 整篇或整章交付前，最后复核标题编号、术语一致性、图表引用、数据前后一致性、摘要与结论对应关系。
